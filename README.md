# Ricorsa

An answer engine that learns you. Live web citations, a recursive learning loop that makes the identity graph smarter instead of the model, and a prepaid business wrapped around it: Auth0 sign-in, 500 gas at signup, recharges by card (Finix) or PayPal with a card on file and auto-recharge, everything metered in gas, Cloudflare D1 for storage, and a push-to-deploy pipeline onto Cloudflare Workers.

## Run it locally in five minutes (no external services)

```bash
npm install
cp .env.example .env.local
npm run db:migrate:local
```

Edit `.env.local` and set these three lines, leaving everything else empty for now:

```
DEV_FAKE_USER=1
DEV_MOCK_LLM=1
AUTH0_SECRET=0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
```

Then:

```bash
npm run dev
```

Open http://localhost:3000/app. You are signed in as a fixed development user, answers stream from a canned stub, and a local D1 database lives in `.wrangler/state`. The whole loop works: ask, see sources, watch the answer stream, see what was learned, open the Graph page. The two `DEV_` flags are ignored in production builds.

To use real models and live web search locally, add `ANTHROPIC_API_KEY` and remove `DEV_MOCK_LLM`.

## Production setup, in order

Everything runs in one Cloudflare account plus five outside services: Auth0 (sign-in), Moonshot AI (Kimi models), Brave Search (live web results), Finix (card billing) and PayPal (billing).

### 1. Cloudflare

Create a D1 database called `ricorsa` (dashboard: Storage & Databases, D1) and put its id in `wrangler.jsonc` under `d1_databases`. Create a user API token with the "Edit Cloudflare Workers" template plus Account: D1: Edit, Zone: DNS: Edit, Zone: SSL and Certificates: Edit and Zone: Zone: Read, scoped to the account and to all zones (or just ricorsa.com). Use the Workers Paid plan: answers stream for 20 to 90 seconds and the Free plan's 10 ms CPU limit is too small.

### 2. Sign-in (Auth0)

Create a Regular Web Application in Auth0. Set:

- Allowed Callback URLs: `https://ricorsa.com/auth/callback` (and `http://localhost:3000/auth/callback` for local use)
- Allowed Logout URLs: `https://ricorsa.com` (and `http://localhost:3000`)

You need `AUTH0_DOMAIN` (no `https://`), `AUTH0_CLIENT_ID`, `AUTH0_CLIENT_SECRET`, `AUTH0_SECRET` (`openssl rand -hex 32`) and `APP_BASE_URL=https://ricorsa.com`. Turn on the social connections you want (Google, Microsoft) in the Auth0 dashboard; the app links to `/auth/login?screen_hint=signup` for sign-up and `/auth/login` for sign-in. Until these are set, the marketing pages work and the app pages answer with a short "being set up" notice.

### 3. Models and search (Brave)

Every model provider Ricorsa talks to speaks one of two wire protocols, Anthropic's Messages API or the OpenAI-compatible chat completions API, and `src/lib/providers.ts` keeps the registry: Anthropic, Moonshot (Kimi), OpenAI, Google (Gemini), xAI (Grok), Mistral, DeepSeek, Groq, OpenRouter, Together and any custom OpenAI-compatible endpoint by base URL. A provider is configured by a key in the environment (`ANTHROPIC_API_KEY`, `KIMI_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `XAI_API_KEY`, `MISTRAL_API_KEY`, `DEEPSEEK_API_KEY`, `GROQ_API_KEY`, `OPENROUTER_API_KEY`, `TOGETHER_API_KEY`; `*_BASE_URL` to point one elsewhere) or by a key an admin pastes under Settings → Model accounts, which is sealed in the `config` table (`provider:<id>`) and outranks the environment. Adding a key fetches the provider's model list and sends one tiny message, so the exact reply (accepted, key rejected, no credit) is on record; from then on any model the account lists can be chosen as the active model for each part of the product (Fast, Best and Reasoning answers, the Build studio, Discover ideas), saved in the `models` config row and applied at once (`PUT /api/admin/models`, `PUT|POST|DELETE /api/admin/providers`). A provider that refuses is set aside for ten minutes and the tier falls to the next model that works, so the product keeps answering. Routing follows the model's family: a `claude-*` id goes to Anthropic and a `kimi-*` id to Moonshot, or to a custom endpoint or aggregator the admin added that lists it, never to another catalog provider that happens to list the name (Moonshot lists Claude ids as aliases for its coding plans and answers "not found or permission denied" to an ordinary key). A provider's own model is trusted when an admin configured it for a tier or it has answered before, whether or not the provider's list has caught up with it (Moonshot's list lagged K3 by weeks); a provider that answers 404 for a model sets that pair aside for an hour, and one that runs past a structured call's time limit for ten minutes. `BRAVE_API_KEY` from brave.com/search/api powers web search. Model ids default to `kimi-k3` for every tier, with thinking effort low for Fast, medium for Best and max for Reasoning (`REASONING_QUICK`, `REASONING_DEFAULT`, `REASONING_COMPLEX`; K3 itself takes only low, high and max, so medium is sent as low); override the ids with `MODEL_DEFAULT`, `MODEL_QUICK`, `MODEL_COMPLEX`. Structured calls (query planning, Home suggestions, Discover ideas; `quickJson` in `src/lib/llm.ts`) turn thinking off on Kimi K2.5 and K2.6 (`thinking: {type: 'disabled'}`), ask K3 for low effort with room for its thinking on top of the answer, use Moonshot's JSON mode, retry a cut reply once with twice the room, and move to the next model when one is unknown, refused or past its time limit (a minute for planning, two for an idea set). The Build studio writes whole apps on `MODEL_BUILD` and Discover ideas on `MODEL_IDEAS`, both `claude-fable-5-1` by default through the Anthropic Messages API (`ANTHROPIC_API_KEY`; adaptive thinking with `EFFORT_BUILD` and `EFFORT_IDEAS`, low to max, default high; the system prompt is cached). Any `claude-*` id routes to Anthropic and any other id to Kimi, so a tier can be moved between providers by changing its id. When Anthropic cannot serve (no key, key rejected, no credit, unknown model, overloaded) builds fall back to the fast Kimi code model (K2.7 code highspeed, then K2.7 code, then K3) and ideas to K3; the studio says so under the version, with what Anthropic answered, and Settings has an admin "Model accounts" check (`/api/admin/models`) that probes Anthropic with one tiny message and reports the exact reply. After the browser check the builder answers findings and local change requests with `<edits>` (find and replace blocks applied by `applyEdits` in `src/lib/build.ts`) rather than rewriting the whole document. Ricorsa checks the Kimi account's model list and falls back to the best available Kimi model when a configured id is missing. Every version the studio writes is opened in a real browser before it is called done (Cloudflare Browser Run, binding `BROWSER`, `src/lib/build-run.ts`): the exerciser in `src/lib/build-exerciser.ts` presses every control, opens every screen, records errors, dead controls, missing screens, dialogs, network requests, blank renders, reload failures and phone-width overflow, and the findings go back to the builder for up to two repair rounds; without the binding the static audit in `src/lib/build-audit.ts` runs instead. A built app has a live line to Ricorsa's model: inside the studio frame and on `/app/run#<version id>` (the Open button) the host page injects `window.ricorsa` (`public/app/assets/bridge.js`), and `window.ricorsa.ask(prompt, { system, onText, search, history })` is relayed with the person's session to `POST /api/apps/ask`, which searches the web when asked, hands the model the person's profile and the app's instructions, streams the answer back into the frame and counts one question against the plan; the builder is told to use it for anything a model should do and to say so when a downloaded copy has no line. The browser check stubs the line so those flows are pressed too. Admins can grant Essentials, Professional or Enterprise to an email address from Settings (`/api/admin/grants`, table `grants`); the plan lands on the account at the person's first sign-in with that address. Point `KIMI_BASE_URL` elsewhere for any OpenAI-compatible endpoint. Searches are metered per answer and priced into the cost estimate (`WEB_SEARCH_USD` in `src/lib/plans.ts`). Files attached to a question (`/api/files`, `src/lib/files.ts`) are read into text once: text and code directly, PDFs with pdf.js (`unpdf`) and Word/Excel/PowerPoint from their XML (`fflate`), and only scans, images and older binary formats through Moonshot's Files API (purpose `file-extract`, retried when busy, the upload deleted right after); the text is stored on the thread and handed to the model ahead of the question, and the web is skipped for that question unless it asks for it. The file itself is kept in R2 (binding `FILES`, bucket `ricorsa-vault`, US jurisdiction; `src/lib/storage.ts`) so it can be opened in the app's viewer: PDFs and images through the browser's own viewers at `/api/files/:id/content`, everything else drawn by the sandboxed renderer page `public/app/assets/viewer.html` (Word with docx-preview, Excel with SheetJS, PowerPoint with PPTXjs, plus Markdown, HTML, JSON, CSV and code), falling back to the extracted text. Stored files are deleted with their thread, with the account, and when a pending upload expires. Per-plan limits live in `caps.files`.

The stable instruction prefix is marked for prompt caching, and follow-ups cache the conversation prefix, which is where most of the input tokens are.

### 4. Card billing (Finix)

Cards are the main way to pay; PayPal stays as the second. You need a Finix live account with a merchant that processes (and, for testing, a sandbox account). Set two secrets on the Worker, `FINIX_USERNAME` and `FINIX_PASSWORD` (the API key pair from the Finix dashboard), and `FINIX_ENV=sandbox` while testing (live otherwise). That is the whole configuration: on first use `src/lib/finix-setup.ts` reads the merchant and the application from the account, registers the webhook at `APP_BASE_URL/api/billing/finix/webhook` with a bearer token of ours and seals the token and Finix's signing key in the `config` table under `finix:<env>`, and reconciles on every cold start. No subscription plans are created any more (Essentials and Professional are retired; the plan ids already in the record stay so their subscribers still resolve).

How it flows: the Recharge page loads Finix.js from js.finix.com (never bundled; the card fields are iframes Finix serves, so the number never touches ricorsa.com). `RechargeBlock` is the page's working part: the amount tiles and the custom amount, the Recharge Agreement box, the auto-recharge box, the order summary, and the pay step, which is one click with the card on file or the card fields (`FinixCheckout`) for a new card, with PayPal behind a link. On submit Finix.js hands back a one-use token; `POST /api/billing/finix/recharge` makes or reuses the person's buyer identity (`finix-buyer.ts`, `users.finix_identity_id`), saves the card as a payment instrument and as the account's card on file (`users.finix_instrument_id`, brand and last four), records the agreement and its version, debits the card once for the amount with an idempotency id (`src/lib/recharge.ts`, `chargeCard`; the transfer's tags carry the account, the dollars and the gas), and credits the gas through `creditGas` when the transfer has succeeded, or leaves it to the webhook when it is still pending (202). `POST /api/billing/finix/card` replaces the card on file without a charge. The webhook verifies the bearer token and the `Finix-Signature` header (HMAC-SHA256 of `timestamp:body`, five-minute window), records each event once, re-reads the subscriptions from before so those accounts follow Finix's current state, and credits a settled transfer once however many times it is reported (`kind` auto or recharge from the tags). Customers never see the processor's name or its error text: a card Finix will not take comes back as a plain sentence (`customerMessageFor`).

Auto-recharge (`autoRechargeIfNeeded`): when it is on, the card on file is charged the person's chosen amount whenever the balance falls below their threshold (200 gas by default), at most once in 24 hours, only with the agreement on record. It runs after a charge lands (`topUpIfLow`, which the ask, build, Discover, app and browser routes call once the work is paid for; the ask and build streams then send a `gas` event the app turns into a toast) and from the gauge's refresh (`/api/me`, in `after()`). The day's slot is claimed on the row before the charge, so two requests arriving together make one payment, and the claim's time is the transfer's idempotency id. A failed charge counts; the third switches auto-recharge off, the Account page says so, and a new card resets the count. `GET`/`PUT /api/billing/auto-recharge` read and change it from the Account page (`AutoRechargeControls`).

To exercise all of it without moving money: `node scripts/test/mock-finix.mjs` stands in for Finix and PayPal (the variables to point the dev server at it are in its header), and `node scripts/test/prepaid-test.mjs` runs the flows end to end against the dev server and the local D1 (welcome gas once, bounds and the agreement, the card on file and one-click recharges, declines, a pending payment settled by webhook and not credited twice, auto-recharge once a day and off after three failures, the PayPal path, the retired plans, the pages' copy and the out-of-gas messages).

### 5. PayPal

You need a PayPal Business account and a REST app (Developer Dashboard). Set `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET` and `PAYPAL_ENV` (`sandbox` while testing, `live` for real billing). The Recharge page passes the client id to the browser to render the buttons, behind the "Pay with PayPal instead" link.

A recharge through PayPal is a one-time order (`POST /api/billing/paypal/gas`, `op` create then capture): the server creates the order for the whole-dollar amount chosen with the account's id on it, captures it after approval, checks it is this account's, completed, in US dollars and for an amount in range, and credits the gas once per order. PayPal keeps no card with Ricorsa, so auto-recharge is not offered with it.

Subscriptions are no longer sold (see Gas and metering below), but the ones from before run until canceled, so the Subscriptions machinery stays: the catalog product, plans and webhook the app created in the `config` table (`src/lib/paypal-setup.ts`), webhook deliveries verified with PayPal's signature endpoint, recorded once and applied by re-fetching the subscription (`src/lib/billing.ts`), and cancel from the Account page. A subscription to a retired plan approved after October 7, 2026 is canceled at PayPal before it bills and the person is pointed at a recharge (`POST /api/billing/paypal/subscribe` answers 410).

### 6. Deploy (Cloudflare Workers Builds from GitHub)

Push this repository to GitHub. In the Cloudflare dashboard open Workers & Pages, Create, Continue with GitHub, pick the repository and use these settings:

- Build command: `npm run cf:migrate && npx opennextjs-cloudflare build`
- Deploy command: `npx opennextjs-cloudflare deploy`

Every push to `main` then applies the D1 migrations, builds with the OpenNext Cloudflare adapter and deploys. `wrangler.jsonc` carries the non-secret configuration as `vars` (app URL, Auth0 domain and client id, PayPal client id, model ids) ; attach the custom domains `ricorsa.com` and `www.ricorsa.com` once in the Worker's Settings, Domains & Routes (the zone is on Cloudflare, so DNS and certificates are handled for you). Add the secrets in the Worker's Settings, Variables and Secrets: `AUTH0_CLIENT_SECRET`, `AUTH0_SECRET`, `ANTHROPIC_API_KEY`, `PAYPAL_CLIENT_SECRET`, `FINIX_USERNAME`, `FINIX_PASSWORD`. Deploys keep secrets; they only replace the plain `vars`.

To deploy from your own machine instead: `npx wrangler login`, then `npm run db:migrate:remote` and `npm run cf:deploy`, and set the four secrets with `npx wrangler secret put NAME`.

## Gas and metering

Ricorsa is prepaid since October 7, 2026. Every account starts with 500 gas (`RECHARGE.signupGas`, granted once per account in `grantWelcomeGas` when the row is made, and to accounts from before on their next visit), everything metered costs gas, and when the gas runs out the person recharges on `/pricing` (the Recharge page; `/recharge` goes there too): whole dollars from $20 to $5,000 at 40 gas per dollar (`RECHARGE` in `src/lib/plans.ts`: the rate, the bounds, the tiles with their labels, the auto-recharge defaults, the agreement version), by card on the page or through PayPal. Gas never expires. There is no subscription and every feature is on for every account with gas (`capabilityPlanKey` gives everyone the Professional capabilities: the full identity graph, Research, Discover, the Build studio, the Ricorsa Browser, 25 connectors, 100 Spaces); Enterprise stays as the contract tier (priced per organization, a monthly gas allowance and higher limits, set from the Manager Console). Essentials and Professional are retired (`RETIRED_PLANS`): the subscriptions that exist keep billing and keep their monthly allowance until canceled, the Account page shows a Plan card only for them, and the subscribe routes answer 410 `plans_retired`.

Everything metered is priced in one unit, gas (`GAS` in `plans.ts`): a question on the Fast or Best model 1, a question on the Reasoning model 3, a Research report 10, a Discover idea set 25 (a cached set served again is free), an app version in the Build studio 250, a browser action 1 and a minute in control of the browser after a take-over 1, a question a built app asks through its live line 1. Bought gas lands in `users.gas_balance` with a row in `gas_purchases` (provider `finix`, `paypal` or `ricorsa` for the welcome gas; `kind` recharge, auto or welcome; the agreement version), and is spent after any monthly allowance the account carries. `src/lib/usage.ts` is the meter: `assertQuota`, `assertBuildQuota`, `assertIdeaQuota`, `assertBrowseQuota` and `assertAppQuota` run before the work and answer 429 `gas_limit` (or 402 `subscription_inactive` for a lapsed subscription) with messages that name what the thing costs, what is left and how to recharge, never a provider, a plan or a dollar cost of ours, and `chargeGas` lands the real cost when the work is done. Each `done` event of `/api/ask`, `/api/build`, `/api/apps/ask` and each take-over frame carries a receipt `gas: { cost, remaining }`, a `gas` event follows when auto-recharge ran, `/api/discover` returns a receipt with a new set, and a finished turn keeps its cost as `turn.gas`; `/api/me` returns the whole `gas` state (allowance, used, balance, remaining, the cost table and labels, the recharge rate, the auto-recharge state and the card on file). The app shows one gauge for all of it: a row in the sidebar (figure, bar against the welcome gas or the auto-recharge amount, pulse and a `-N` tag on every charge), a Recharge row beneath it, a cost chip in the composer, a receipt tag under each answer, the Discover button's `25 gas`, the studio's cost line, the take-over minutes, and a Gas sheet with the stand, the card and auto-recharge line, and the price list. The Recharge Agreement (`/recharge-agreement`, versioned in `RECHARGE.agreementVersion`) is what the person ticks before paying: what a recharge is, that gas does not expire, refunds, the card on file, auto-recharge, PayPal and taxes; the version is recorded with the account and with each purchase. The Account page shows the gas on hand, the card on file with Update card, the auto-recharge switch, threshold and amount, and every credit (recharges, automatic ones, the welcome gas). Admins are not metered (the gauge says Unlimited). Usage rows in the `usage` table carry token counts and an estimated cost so you can watch margin per user; the price constants near the bottom of `plans.ts` are the ones to update when model prices change.

## The identity graph

Each answer ends with a `<learned>` block the model writes about the person: intent, topics, entities, goals, expertise levels, style. `mergeLearned` folds it into a weighted graph: repetition strengthens a node, everything decays a little on each event, faded nodes are pruned, and nodes learned together are connected. `graphPromptBlock` renders the top of the graph into the system prompt for the next question. The person can pause learning, forget a node, export the graph, or reset it; all of that is real API and lives under `/api/graph`.

The `<learned>` block also names up to three real places the work is about (a city, a county, a site, an address). They become entity nodes flagged `place`, and after the answer has been sent `src/lib/geo.ts` looks each one up and writes a GeoJSON point (plus the display name, the kind and a bounding box) onto the node. The geocoder speaks the Nominatim search API: OpenStreetMap's public instance by default (one request a second, an identifying User-Agent, attribution on the map, all honored), or any compatible endpoint set with `GEOCODER_URL` and `GEOCODER_KEY` (LocationIQ, a hosted or company Nominatim); `GEOCODING=off` turns it off. Lookups are cached in the `config` table (`geo:<slug>`, six months for a hit, a week for a miss). The Graph page's Map view (`public/app/assets/graphmap.js`) draws the anchored nodes on Natural Earth land, lakes and borders (`public/app/assets/world-110m.json`, with six 1:50m longitude bands fetched when the view is close enough) in the colors of their cortex, with the same time scrubber, search, labels, cortex focus and node panel as the brain.

The Graph page's lists are live: each chip carries its weight, marks what is new, strengthening, fading or a place, lights its node in the brain on hover and opens the node panel on click; the toolbar sorts and filters them, a pinned cortex narrows them to its types, and the time scrubber hides what had not been learned yet. The node panel opens Discover centered on the node (`POST /api/discover` with `anchor`), starts a thread about it (origin kind `graph`), shows it in the brain or on the map, and lists the Discover ideas that draw on it; Discover's idea chips link back to the node or the type in the graph (`#/graph?node=` and `#/graph?type=`).

## Memory

Every finished answer and every attached file is cut into passages and kept in the `memories` table for that account only (`src/lib/memory.ts`). When a new question comes in, the passages that bear on it are recalled (keywords over the table, scored in code by term overlap weighted by rarity, a verbatim phrase of the question, and recency; at most one source per turn and two per thread, never from the thread being answered) and numbered after the web sources under the labels "Your threads" and "Your files", so the model can cite "your earlier answer" or "your file" and the reader can open the source: the link goes to that thread, scrolled to that turn (`/app#/thread/<id>?turn=<turnId>`). The first answer on an account also fills the memory from its most recent hundred threads and their files, once. Deleting a thread deletes what was remembered from it; `MEMORY=off` turns the whole thing off. When the Worker also has a Vectorize index bound as `VECTORS` and Workers AI as `AI` (both added in `wrangler.jsonc`; create the index with `wrangler vectorize create ricorsa-memory --dimensions=768 --metric=cosine`), the same passages are embedded with `@cf/baai/bge-base-en-v1.5` and recalled by meaning as well; both bindings are detected at run time, so nothing else changes.

## Running it as a service

Customers never see which provider wrote an answer or a version, nor any provider error or billing state; that is operator information, shown to admins only (the studio's model and fallback lines, Settings → Model accounts). When a provider refuses, answers and builds fall back to the next model and the customer sees a normal result. `GET /api/health/models` (no sign-in) answers 200 when every configured model account responds and 503 when one refuses (no credit, rejected key, unknown model), with no details: point an uptime monitor at it (Cloudflare Health Checks, UptimeRobot, Better Stack) with an email or phone alert, and the operator hears before a customer does; the probe is cached for five minutes. Admins also get a banner in the app while an account is refusing. On the Anthropic side, turn on auto-reload with a spend limit in the Console so the balance never reaches zero; the key should live in a workspace of the same organization that holds the credit.

## Connectors and Spaces

A connector is available everywhere by default. It can instead be limited to one or more Spaces (Where on its card, or Add to this Space on the Space page, which creates it limited to that Space), and then only threads in those Spaces are given its tools; a thread outside any Space, or in another Space, never sees it. The scope is the `space_ids` column on `connectors`; `connectorsForModel` in `src/lib/connectors.ts` applies it per thread, the Space page lists what a thread there can use, and deleting a Space takes it out of every connector's scope (a connector left with no Space becomes available everywhere).

## Website connectors

Connectors → Add connector → Website takes any public address. Ricorsa walks the site from that page (same host, up to the number of pages chosen, sixty at most), fetching each page plainly and opening it in the headless browser when the document is an application with little static text: the text on screen is kept instead, the links it shows are followed, and its own tabs and menu buttons are pressed so screens that only appear on a click are read too (`src/lib/sites.ts`). Pages are stored per connector (`sites`, `site_pages`) and searched in memory. The model reaches them through the connector's own MCP endpoint, `/api/sites/mcp/<connector id>` (bearer token = the connector's secret), with `site_search`, `site_read` and `site_pages`; hits and read pages become numbered sources with the real page URLs, so answers cite them and the citations open the page. Read again replaces the pages; removing the connector removes them. Private and local addresses are refused (`SITES_ALLOW_LOCAL=1` lets development read a site on this machine).

## Ricorsa's browser: Open the site

On the Professional and Enterprise plans the composer has an "Open the site" control. With it on, the person names a website and says what to do there, and Ricorsa opens the site in its own browser (Cloudflare Browser Run, the `BROWSER` binding the Build studio already uses; `src/lib/browse.ts`) and works it one action at a time while they watch: a pane beside the thread shows a screenshot after every step, the step list as it grows, the page it is on, and a Stop button. The model gets eight tools of Ricorsa's own (`browser_open`, `browser_click`, `browser_type`, `browser_select`, `browser_scroll`, `browser_back`, `browser_read`, `browser_find`; `LocalToolSet` in `src/lib/llm.ts`, offered beside the connectors' MCP tools). After each action the page is read back as text in reading order with every link, button and field numbered (`src/lib/browse-snapshot.ts`, run inside the page), so the model acts on controls by number; screenshots go to R2 under `browse/<user>/<turn>/<n>.jpg` and are served to the owner by `/api/browse/shot/:turnId/:n`. Every page the browser shows is numbered as a source the answer cites, and the steps are stored on the turn (`turn.browser`) so the pane can be reopened later from the answer's note.

Take over and hand back (phase 2). After a browsing answer the page stays open for five minutes (`KEEP_ALIVE_MS`; the browser is launched with `keep_alive` and disconnected from, not closed, and the session id is kept server-side in `browse_sessions`). The pane then offers Take over: the person operates the page themselves through a picture that refreshes every second or two, with clicks, typing, keys, scrolling, an address field, back and reload sent to the page (`POST /api/browse/take/:turnId` with `op` start, act, frame or end; `src/lib/browse-live.ts`). Each move reaches the browser again by its session id, acts, takes the picture and lets go, so nothing is held between moves; what the person types travels through the server to the page and is never logged or stored, and the model never sees it. A minute in control costs 1 gas (charged as the minutes pass, so a tab closed without Done still pays only for its minutes; each frame carries the receipt), a take-over is capped at thirty minutes, and one page is open per account at a time. Hand back keeps the page open and prefills a follow-up with Open the site on and `resumeTurnId`, so the next answer carries on from the same page (`BrowseSession` reconnects instead of launching; the guide tells the model the person may have signed in or done a step); Done closes it. The moments are recorded on the turn as steps (You took over the page; You handed the page back after N minutes, with a closing picture). When the person typed into a password field while in control, ending the take-over asks whether to keep that site's sign-in: the cookies for the registrable domains visited (`Network.getAllCookies`, filtered) are sealed with the connector secret box into `browse_sites`, restored by `browser_open` the next time Ricorsa opens that site for them, listed on the Account page under "Sites Ricorsa stays signed in to" with a Sign out that deletes them (`GET /api/browse/sites`, `DELETE /api/browse/sites/:id`), and named to the model in its guide so it knows a site may already be signed in. In development, `BROWSER_WS_ENDPOINT` takes precedence over the local binding stub because a Chrome reached that way keeps its pages across a disconnect, the way Browser Run does; pages are found again by a `window.name` marker.

What holds whatever the model asks: only public websites (the same address check as website connectors), no sign-ins or account creation, and no field that takes a password, a one-time code, a card number or a government id is ever filled (such fields are listed as protected and never get a number; a typed value that is itself a card or social security number is refused too). Cookie banners are declined, not accepted. The guide the model follows is `browserGuide` in `src/lib/browse.ts`: do what was asked and stop before anything that would commit (send, order, pay, delete, sign up) unless that exact step was asked for. Each action (an open, a click, a typed field, a chosen option, a scroll, a back) costs 1 gas, charged with the answer (`GAS.browserAction`; `usage.browser_actions` keeps the count too, migration 0015; `assertBrowseQuota` answers 402 `upgrade_required` on plans without the browser and 429 `gas_limit` when the gas is gone, naming the reset and the next plan, never a cost in dollars; the number of actions one answer may take is capped by the gas left, up to `MAX_ACTIONS_PER_ANSWER`). One answer may take at most 40 actions and 70 steps within 150 seconds, after which the model is told to write from what it has. Reads and finds are free. Free and Essentials see the control locked; pressing it explains what it does and what the plans include. Without the binding the request answers 503 `browser_unavailable`. In development, point `BROWSER_WS_ENDPOINT` at a Chrome started with `--remote-debugging-port` (and set `SITES_ALLOW_LOCAL=1` to open a site on this machine); the mock model then works the named site for real so the pane can be exercised.

## Consoles in answers

When an answer is about the person's own setup or something they can act on in Ricorsa (their connectors, the apps they built, an idea to build, what to ask next), the model may place one interactive console inside it: a fenced block tagged `console` holding a JSON card of rows, each with a status pill and up to three buttons. The guide and the context the model gets (connector ids and states, presets that can be added, recent apps) are in `src/lib/console.ts`; the app renders the card (`mountConsoles` in `public/app/assets/app.js`) and runs a fixed set of verbs: open a route, ask a follow-up, build an idea, turn a connector on or off, add a preset, open an app, open a link, copy text. Ids are checked against the person's account before anything happens, and the prose still carries the substance.

## Answers and citations

Focus (Web, Academic, Technical, Legal, Writing, Math, Code) shapes the prompt and the search: Academic and Legal add site filters for scholarly and primary legal sources, Technical asks for specifications and standards, Code for documentation, Writing skips the web. Each answer starts with retrieval: one Brave query for a normal question (none for Writing focus), four to six planned queries plus a read of the top pages in Research mode. The merged, numbered results are pushed to the browser before the model starts and handed to the model as context after the question; it cites them with `[n]` markers that the client renders as chips. Connectors are offered to the model as functions; when it calls one, Ricorsa calls the MCP server and returns the result, until the model answers. Answers that hit the output limit continue in partial mode. Earlier answers are fed back into follow-ups with the markers stripped.

## Files: ask, find, highlight

A file attached to a question is read in full and, since version 1.2, also cut into passages that remember where they came from (`src/lib/passages.ts`: `[Page n]` for PDFs, `[Slide n]` for decks, `[Sheet: name]` with row ranges for workbooks, sentence groups for everything else). The passages that bear on the question (keyword scoring, with a floor of two per file so a broad question still has something to point at, and up to twelve when the question is a lookup such as "where does it mention") are numbered after the web sources under the label "Your files", each with its location and a link that opens the file in the viewer at that passage: `/app#/thread/<id>?turn=<turnId>&file=<fileId>&p=<page>&hl=<the sentence that answers>`. The model is told to cite them by number, so a claim from a file opens the file at the sentence it came from.

The viewer (`public/app/assets/viewer.js`, sandboxed) draws PDFs with pdf.js (pages as they scroll into view, each with a text layer), Word with docx-preview, workbooks as a grid, decks with PPTXjs, and the rest as text or code. Every kind has Find in this file (matches across the whole document, Enter and Shift+Enter walk them, the page is named for PDFs) and highlight (a citation's snippet is located in the rendered text, whitespace-insensitive, and the whole sentence is marked). Ask about this opens a pane beside the document: the question runs as a turn on the conversation the file belongs to, with the file attached again as the primary material, the answer streams in the pane, and a citation of the file lights the passage in place without leaving the viewer. A file still only attached to the composer hands the question to the composer instead.

## Provenance

Everything created from a graph carries a cryptographic id. When Discover generates ideas, each one is hashed (SHA-256) over a non-reversible subject id, the exact fingerprint of the graph it was drawn from (every node id, weight and count), the category, the idea text and the moment of generation. A thread started from an idea stores that id and fingerprint as its origin, every turn chains a new hash onto the previous one, and any node the thread adds to the graph records the turn and idea it came from. The thread menu has a Provenance view with the full chain, and the Graph page has one for the whole graph (`GET /api/graph/export?summary=1`: fingerprint, subject id, counts, the latest lineage entries). Export on the Graph page downloads the graph with its provenance (`GET /api/graph/export`): the fingerprint and how it is computed, every node with its weight, origin and map anchor, the connections, the intents, and on full-graph plans the lineage chain of every thread (its origin, each turn's hash and the nodes each turn added); the file name carries the fingerprint. `src/lib/hash.ts` is the single place the hashing lives if you later want to anchor those ids somewhere external (a ledger, a timestamping service, a verifiable credential).

## Security notes

- The browser never talks to PayPal, Moonshot AI or Brave directly, and never holds a key. Card details go only to Finix's own fields (iframes from js.finix.com) and come back as a one-use token; the page never sees the number.
- Subscriptions are only ever applied from PayPal's or Finix's own subscription object, never from what the browser claims; the plan and the account come from the processor's plan id and tags.
- Every API route resolves the signed-in user first; threads, Spaces and graphs are always filtered by owner.
- Security headers are set in `next.config.ts`. Put Cloudflare's WAF and Turnstile in front of `/auth/login` if free-tier abuse shows up.

## Manager Console

The staff console (customers, sign-ups, licenses, trials, communication, invoicing and billing) is a separate app in `console/`, deployed as its own Worker at https://manage.ricorsa.com with its own database and Auth0 application. It reads this product's database for live account data (accounts, their gas on hand and purchases, the subscriptions from before with their billing cycle, usage with cost) and writes two things: plan grants (statuses `TRIAL` and `LICENSED`, which `src/lib/plans.ts` treats as granting until `planRenewsAt` passes; Enterprise is the tier set this way) and `users.allowance`, a monthly gas allowance above the tier's (`gasPerMonth`; an Enterprise contract's figure, a goodwill raise), which `limitsFor` in `src/lib/usage.ts` applies. Its dashboard reads the paying base as cohorts by plan and cycle (MRR, trailing cost, gross margin, churn, LTV) and drafts true-up invoices for the annual accounts that spent more gas than their plan's allowance. See `console/README.md`.
